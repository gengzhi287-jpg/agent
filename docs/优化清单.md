## 一、Bug / 正确性问题（P0）

### 1.1 Content-Type 检查无效 ✅ 已完成 `crawler.py`
- 现状：`if "image" not in ctype and not ctype: pass` 是空逻辑，服务端返回 HTML 错误页也会被当图片下载。
- 方案：改为 `if ctype and "image" not in ctype: return None, None, "非图片内容"`。

### 1.2 去重记录先于写盘 ✅ 已完成 `saver.py - save()`
- 现状：MD5 先加入 `_seen` 再写文件，写盘失败后该图被永久标记重复，重跑无法恢复。
- 方案：写盘成功后再加入集合并持久化。

### 1.3 去重文件全量重写 ✅ 已完成 `saver.py - _persist_seen()`
- 现状：每保存一张图就排序 + 全量序列化整个集合写盘，图越多越慢。
- 方案：追加写入新 hash，或任务结束 / 程序退出时统一持久化。

### 1.4 下载失败不补位 ✅ 已完成 `app.py - _process_url() / _process_keyword()`
- 现状：`urls[:count]` 截断后，下载/校验失败不会取后续候选，实际保存数常远少于 count。
- 方案：按"保存成功数达标"为目标循环拉取候选，设最大尝试上限。

### 1.5 锁内返回 `app.py - _process_keyword()`
- 现状：`return dict(...)` 写在 `with _state_lock:` 块内，功能正常但易误读。
- 方案：先在锁内取快照，锁外 return。

## 二、性能优化（P1）

### 2.1 下载与校验并行化（收益最大）✅ 已完成
- 现状：`_process_keyword` 串行 for 循环，每张图同步等待下载 + 多模态 LLM 校验；Agent 路径 `collect_one` 把 concurrency 写死为 1。
- 方案：用已有的 `ThreadPoolExecutor` 并行下载+校验（默认 4 并发），Agent 路径同样启用。
- 预期：整体耗时下降 60%+，可在简历中量化描述。

### 2.2 内容校验两级过滤 ✅ 已完成（改为去重前置+结果缓存，见内文备注）
- 现状：每张图一次多模态 LLM 调用，成本高、延迟大。
- 方案：先用图文 embedding 相似度批量粗筛，仅对边界样本调多模态模型精判。
- 实施备注（2026-08-31）：已验证套餐 endpoint 的 embeddings 接口仅支持文本输入（图片输入返回 400），故改为等效低成本方案——① 多模态校验前先查 MD5 去重，重复图不再调 LLM；② 校验结果按图片 MD5 持久化缓存（classify_cache.json），同一图片跨任务不再重复调用。

### 2.3 Bing 解析失效检测 ✅ 已完成
- 现状：Bing HTML 正则抓 `murl`，页面改版即失效且无感知。
- 方案：连续两次解析为空时记日志，并提示用户配置 Pixabay / Pexels Key 作为稳定源。

## 三、架构 / 代码质量（P2）

### 3.1 消除 URL 归一化重复代码 ✅ 已完成
- 现状：去 `/chat/completions` 后缀的逻辑在 `agent.py` 和 `classifier.py` 重复 3 份。
- 方案：抽成公共函数（如 `utils.normalize_chat_url`）。

### 3.2 拆分 app.py（649 行）✅ 已完成
- 现状：Flask 路由、任务状态机、采集管线、Agent 调度、报告生成全在一个文件。
- 方案：拆出 `pipeline.py`（采集逻辑）、`state.py`（任务状态），路由层只做参数解析与响应。

### 3.3 多任务支持 ✅ 已完成（任务队列）
- 现状：全局 `_state` 单任务设计，并发请求直接拒绝，前端刷新后状态丢失。
- 方案：引入任务 ID + 每任务独立状态，支持任务排队与历史状态恢复。

### 3.4 Agent 轮次上限可配置 ✅ 已完成
- 现状：`max_iter=15` 硬编码，达上限后静默返回 None。
- 方案：移入 config.yaml；达上限时让模型补一次总结而非直接结束。
